# 项目目标：通过本地 GUI 维护 War Thunder Wiki 数据

目标基线：2026-10-23。本文件描述产品目标与技术路线，不表示全部功能已经实现。

## 最终目标

将 Wiki 需要的载具、科技树、武器和弹药数据，转换为可由 MediaWiki JSON 数据页与 Scribunto Lua 模块消费的结构。提供有 GUI 的本地工具，支持一键 diff、一键导出 JSON、一键生成页面导入 XML 包，以及按给定国家、军种、载具或依赖集合定向生成更新。

对于给定游戏版本，维护者只需更新或选择合法取得的本地 datamine 包，即可重新解析并更新全部数据，或按站点限制分块导出，或仅生成个别载具及其所需依赖。工具生成可复制源码、精确页面名、上传清单与导入步骤的离线助手。默认不通过机器人编辑 BWiki；以用户手动执行的 XML 导入作为批量部署方式。

游戏版本更新通常只需替换 JSON 数据页。已经开源的转换规则与共用 Lua 模块负责计算和展示，避免逐条手工修改载具页面。游戏数据结构、计算方法或 Wiki schema 改变时仍需要维护转换器或模块，不能保证任何新版本均无需代码适配。

## 当前已实现

- Python 命令行转换器，输入 shop、wpcost、unittags、本地化与部分模型/武器定义。
- 全游戏简化载具与 group 索引；共享改装描述/图标定义和载具本地价格/位置引用拆分。
- 对当前快照全部 44 个 shop 国家/军种分支生成布局，并用同一 Lua 模块完成本地结构验证。
- 美国陆战、中国空军、德国近岸海军三棵测试树，以及 M1A2 共享改装演示。
- JSON + Lua + 共用 CSS/JS 渲染、手动部署助手、包含 14 个测试页的完整 XML 及 ZIP。
- 本地 JSON 引用/大小/XML 回读验证，Lua 两条读取路径验证，部分浏览器交互检查。

当前没有 GUI、版本差异分析、通用导入包分块器或完整的载具/武器/弹药详细计算。现有验证绑定快照计数；站点素材映射依赖本地 evidence。新克隆的源码仓库不含这些输入，暂不能仅下载源码后直接重建演示。此限制需在第一阶段解决。

## 预期工作流

1. 在 GUI 选择 datamine 根目录、目标 Wiki 配置、输出位置及已部署基线。解析输入版本、来源哈希和 schema 兼容性。
2. 自动检查支持的输入；运行转换及计算，明确报告缺文件、未知字段、缺本地化和未解析参数。
3. 点击 diff：展示新增、删除、字段变化、科技树移动、组成员变化、BR/价格变化，以及仅本地化、素材或布局的变化。
4. 选择全部更新、国家/军种、变更项，或一个/多个游戏代码；预览自动加入的共享依赖和被影响的树。
5. 点击导出 JSON，生成稳定页面名、确定性内容、哈希和清单；在 GUI 设置每个 XML 的最大页面数、页面文本总体积及文件体积上限，预览切片结果，再一键生成完整或增量的多个 XML 文件。
6. 在助手中核对页面、图片与导入顺序，使用具备相应权限的账号手动导入。脚本页权限单独提示，不隐瞒前提。
7. 导入后验收，再将这次输出标为已部署基线。导出成功不等于部署成功；不能自动覆盖该基线。

## 架构边界

使用一套转换内核服务命令行与 GUI。GUI 只负责参数、进度、预览、选择和错误反馈，不复制解析或计算逻辑。推荐先按现有 Python 代码提取库，再实现 GUI；具体界面框架在跨平台与打包验证后确定。

```text
本地 datamine + Wiki 站点配置 + 已部署基线
  → 输入适配器与版本校验
  → 规范化实体与计算规则
  → 引用依赖图和确定性 JSON
  → 语义 diff / 更新选择 / 依赖闭包
  → 页面映射 / 分片 / XML / ZIP / 离线助手
```

实体主要采用游戏内代码作为稳定 ID：载具、group、武器、弹药、改装件均可独立引用。中文本地化随对应数据记录保存；全局载具简化索引保留科技树查询所需的最少信息，详细数据和大型武器/弹药定义按需加载、按稳定键分片。载具本地只保存实例相关的费用、位置、挂载和覆盖，避免复制整个共享库。

每个计算字段须可追溯至输入路径、原始字段与计算规则版本。不得将游戏动态生成、尚未计算或缺失的数据伪装为完整数值；保留明确状态和回退策略。官方 Wiki/BWiki 数据作为对照证据，不能无来源地覆盖游戏计算结果。

站点的旧页面名、文件名与图标等放在独立展示映射/配置中。全游戏转换不应要求人工保存全部网页；缺映射须有可部署的回退和待处理清单。共用渲染模块从 JSON 得到国家、军种、类别和布局，不为每棵树新增代码。

## Diff、选择性更新与稳定输出

- 比较规范化语义，忽略 JSON 键顺序及格式变化；数组中的科技树顺序、组顺序、挂载顺序有语义，不能全部排序。
- 区分游戏输入版本变化、转换规则变化、schema 变化与用户配置变化。相同输入和规则应生成相同 JSON 内容与哈希。
- 首次无基线为全量导出；其后比较明确选定的已部署输出，也可比较两个游戏输入快照。
- 单载具更新要计算依赖闭包：必要的全局索引、武器、弹药、改装定义和树引用同步更新。不能输出会造成悬空引用的“单文件更新”。
- 删除/更名列为待人工处理项。普通页面导入不能自动删除线上旧页，不把删除操作悄悄写进助手。

## JSON 分片与 XML 部署约束

单页 JSON 以稳定 ID 分桶或其他稳定边界拆分，避免一条新增记录导致所有后续页重排。索引记录分片位置、schema、游戏版本和哈希，Lua 按需读取。页数、原始/格式化字节数、解析后内存、加载次数和执行时间均需设预算并测试。

现有 2MiB 单页检查只是一项约束，不等于 Scribunto 全部资源限制。XML 的最大上传大小、单次页数、站点导入权限与执行时间应为站点配置；生成器估算体积并按依赖顺序分包，拒绝输出超过设定预算的单页。跨包部分导入可能导致版本不一致，应有模块兼容校验、明确顺序和重试指引，不承诺跨包原子部署。

### GUI 中的 XML 导出切片

考虑到 MediaWiki 页面导入的上传大小、处理时间及页面数量限制，导出工具必须支持将同一次更新切成多个独立、有效的 XML 文件。此功能属于未来 GUI 的必需能力，当前固定导出包不代表已经实现自动切片。XML 文件切片与 JSON 数据页分片是两个层次：前者改变导入文件的打包方式，不改变页面标题、页面内容或数据引用。

- GUI 提供每个 XML 的最大页面数和页面文本总体积上限，两项独立配置并同时生效；加入下一页将超过任意一项上限时，结束当前切片并开始下一片。不硬编码某个适用于所有 MediaWiki 站点的统一数值。
- 页面文本体积按各页源码的 UTF-8 字节数累计，界面明确单位，不能用字符数替代字节数。另设最终 XML 文件体积上限，按实际序列化后的 UTF-8 字节数校验，计入 XML 转义、页面元数据、文件头和闭合标签；ZIP 压缩后体积不能代替上传 XML 的体积。
- 导出前预览预计分片数，以及每片的页面数、文本字节数、最终 XML 字节数和页面列表。阈值可保存为站点配置，修改阈值后重新计算切片；全量、增量和指定载具更新共用同一规则。
- 页面是最小打包单位，不能将一页源码或一个 XML 元素截断到两个文件。单页连同必要包装已超限时，应定位并报告该页面，阻止将此导出标为可部署；引导提高合理阈值或先对 JSON 数据页分片，不能静默超限、遗漏该页或生成损坏 XML。
- 每片都包含必要的 XML 根节点、命名空间声明与导入元数据，可单独解析、回读和提交导入。命名采用带序号和总片数的形式，例如 `update-0001-of-0012.xml`，保持依赖顺序和确定性的页面排列。
- 随包生成总 manifest 与助手清单，记录游戏版本、schema、导出范围、阈值、各片哈希、页面归属及建议导入顺序。每个选定页面恰好归属一个切片，不重复也不遗漏；重试时允许用户单独选择失败切片，并清楚提示可能已导入的页面。
- GUI 显示切片生成与验证进度，取消或失败时不覆盖已有有效输出。助手明确提示跨片导入不是事务：中途失败可能暂时混用版本，全部必要切片完成并验收后才能将结果标记为已部署基线。

切片验收应覆盖：零页和单页、恰好达到阈值、加入下一页超限、页面数与文本体积分别先触发、中文及 XML 特殊字符的字节统计、单页超限、单片包装开销、所有片的 XML 回读，以及完整清单无重复/无遗漏。验收还需在独立测试 Wiki 中按顺序导入多个切片，核对页面模型、内容与版本一致性。

XML 包含精确标题、命名空间、内容模型和 UTF-8 源码。JSON、Lua、模板与 JS 以正确模型导出，完整包和增量包明确区分。二进制图片单独打包并列出名称、来源和上传步骤；页面 XML 不等于图片上传包。

不依赖 Wiki 机器人。共用模块/样式/脚本一般只在 schema 或展示逻辑改变时更新，数据更新包默认不强制混入它们。首次安装、运行组件升级和普通版本数据更新分别给出明确的导入选择。

## 分阶段交付与验收

| 阶段 | 交付 | 核心验收 |
|---|---|---|
| 1. 可复现核心 | 配置化输入、解除 evidence 硬依赖、版本适配、库化 CLI、合成测试夹具 | 干净克隆按文档配置合法输入即可生成；不依赖作者绝对路径或缓存；原始输入只读 |
| 2. 更新内核 | 基线 manifest、语义 diff、稳定分片、依赖闭包 | 相同输入零差异；单载具变更只影响必需记录与依赖；删除明确报告 |
| 3. GUI | 输入选择、版本状态、diff 面板、更新范围、XML 页面数/文本及文件体积阈值、切片预览、导出按钮和进度/取消 | 非开发者可完成全量及单载具更新；可配置切片上限并核对每片内容；错误可定位并保留日志；取消不破坏已有输出 |
| 4. 完整数据域 | 详细载具参数、武器、弹药及计算规则 | 字段可追溯；跨陆海空代表样例与官方/游戏对照；缺失显式报告 |
| 5. 部署交付 | 按页面数与体积自动切片的全量/增量 XML、分片 manifest、ZIP、助手、回退材料 | 每片均有效且满足配置上限；源码往返一致；页面无重复/无遗漏；无悬空依赖；独立测试 Wiki 多片导入验收 |

测试应覆盖规范化、语义 diff、公式、引用和导入正确性，使用自建小型合成数据夹具。公开仓库不提交游戏数据、游戏图片或完整站点快照；本地真实数据验证与线上验收分开记录。

## 成功标准

维护者更换本地版本后，通过 GUI 完成 diff、选范围、生成 JSON 与 XML/助手，正常数据更新无需逐页编辑。共用模块和导出规则有清晰版本，输出可核验、可重现、可分块导入，并能针对指定载具安全生成完整依赖集合。BWiki 的导入权限和资源限制由验收确认，不能只凭本地预览宣布可全站替换。
